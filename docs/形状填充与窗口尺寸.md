# 形状填充与窗口尺寸

> 从「甜甜圈填不满窗口、四周大量留白」查起，连带挖出的一串问题：拖动时窗体持续变大、窗体自己移动、球体光照方向反了、采样密度不随窗口伸缩、字号是格子的两倍、字符阶梯没归一化、球体压根没在转、窗体难以选中。
>
> 每一节都是「现象 → 根因 → 数值验证 → 修复」。文中所有百分比都是数值仿真实测，不是估计。
>
> 涉及 [`src/components/PetCanvas.tsx`](../src/components/PetCanvas.tsx)、[`electron/main.ts`](../electron/main.ts)、[`electron/windowManager.ts`](../electron/windowManager.ts)。

## 一、留白问题

### 现象

无论窗口调到哪个尺寸，甜甜圈都只占窗口中间一小块，四周留出大片空白。

### 根因

**投影缩放系数 K1 只有正常值的 55%。**

```ts
const K1 = 0.345 * COLS   // 旧代码
```

经典 donut.c 的推导是 `K1 = width * K2 * 3 / (8 * (R1 + R2))`，代入本项目的 `K2=5, R1=1, R2=2` 应为 **0.625 × COLS**。0.345 只有它的 55%。

按实际投影公式数值仿真（COLS=71，对应 320px 窗口），包围盒占画布比例：

| K1 系数 | A=0.9,B=0.4 | A=0.9,B=1.57 | A=1.57,B=0.4 | A=0,B=0.4 |
|---|---|---|---|---|
| **0.345（旧）** | 46% | 49% | 44% | 49% |
| 0.50 | 66% | 71% | 64% | 71% |
| 0.58 | 77% | 83% | 74% | 82% |

即四周各留了约 25%~28% 的空白。

另外三个次要来源：

- **字形锚点偏移**：`textBaseline:'top'` + 左对齐，整个形状系统性偏左上近一格
- **外层 border**：`border: 1.5px` + `box-sizing: border-box` 吃掉四周各 1.5px
- **球体多乘了 1.5**：与 K1 叠加后缩放语义混乱

（球体还有更严重的光照方向 bug 和采样不足问题，见 [5.1](#51-球体光照方向反了主因) / [5.2](#52-采样步长写死格子数却随窗口增长)。）

### 方案：固定拟合常数

```ts
const FIT = {
  donut:  { k: 0.542, ox: 0.5, oy: 0.5 },
  sphere: { k: 0.963, ox: 0.5, oy: 0.5 }
} as const
```

常数是**离线跑数值仿真**得出的：对所有姿态 (A, B) 的投影轮廓求**并集包围盒**，再取「缩放到画布 98% 且任何姿态都不裁切」的最大值。

两者的并集包围盒中心都恰好是 `(0, 0)`，所以 `ox/oy` 都是 0.5 —— 单个姿态下透视会让包围盒中心漂移（最大 `0.187×K1` 横向 / `0.251×K1` 纵向），但对所有姿态取并集后正好抵消。

> 球体的常数一度是 `k=1.123, ox=0.583, oy=0.394`，偏心得很离谱。那是因为当时在拟合一个被光照 bug 砍成 2.7% 的月牙 —— 见 [5.1](#51-球体光照方向反了主因)。修掉光照后回归 0.5/0.5。**拟合常数偏离对称值，往往是上游有 bug 而不是该形状本来就偏。**

### 为什么不用逐帧自适应

最初实现的是逐帧自适应：每帧先量当前姿态的轮廓包围盒，再反算「刚好填满」的缩放和偏移。**仿真数据确实更好**（填充率 91.5%~97.2%，零裁切），但实机跑起来有明显问题：

> 每次鼠标拖动的时候，尺寸都会变化

因为拖动会 `triggerKick` 触发旋转，而自适应缩放会随姿态在 ±6% 之间变化 —— 表现为形状一边转一边「呼吸」。仿真里这是「填充率区间」，肉眼看就是抖动。

**已回退为固定常数。** 代价是填充率从 ~94% 降到平均 74%，换来完全静止的尺寸。

## 二、拖动时窗体持续变大

### 根因：把测量值喂回被测量的对象

```ts
ipcMain.on('win:drag-to', (_e, x, y) => {
  const [w, h] = mainWindow.getSize()                    // 读回当前尺寸
  mainWindow.setBounds({ x, y, width: w, height: h })    // 又写回去
})
```

这个 handler 在拖动全程以 **~60 次/秒**被调用。问题不在 `setBounds` 本身，而在 **`getSize()` 的结果被当成输入写了回去**——这是一个正反馈环。

为什么读回来的值会变？Chromium 在 DIP ↔ 物理像素之间转换用的是**外接矩形**（enclosing rect）：原点向下取整、远边向上取整。

```
物理宽度 = ceil((x + w) * scale) - floor(x * scale)
```

**物理宽度依赖于 x 的小数部分**，不只依赖 w。所以同一个 220 DIP 的窗口，在不同 x 上读回来的尺寸会不一样：

| 缩放 | x = 100..107 时 `getSize()` 的结果 |
|---|---|
| 100% | 220, 220, 220, 220, 220, 220, 220, 220 |
| **125%** | 220, **222**, **222**, **222**, 220, **222**, **222**, **222** |
| **150%** | 220, **222**, 220, **222**, 220, **222**, 220, **222** |
| **175%** | 220, **222**, **222**, **222**, 220, **222**, **222**, **222** |
| 200% | 220, 220, 220, 220, 220, 220, 220, 220 |

拖动时 x 一直在变，于是每帧都可能读到 222 并写回，下一帧在 222 基础上再读到 224……**单调增长**。模拟 300 帧拖动：

| 缩放 | 旧代码 | 修复后 |
|---|---|---|
| 100% | 220 → 220 | 220 → 220 |
| 125% | 220 → **669** | 220 → 220 |
| 150% | 220 → **520** | 220 → 220 |
| 175% | 220 → **669** | 220 → 220 |

这解释了两个现象：为什么是**慢慢**增大（每帧才 +2px），以及为什么**不是所有人都能复现**（100% 和 200% 整数倍缩放下完全不出现）。

### 为什么 `setPosition` 救不了

第一版修复把 `setBounds` 换成了 `setPosition`，以为「只改位置就不会碰尺寸」。**无效** —— Electron 在 Windows/Linux 上的 `NativeWindowViews::SetPosition` 内部实现就是「读当前 bounds → 换掉原点 → 调 SetBounds」，尺寸照样往返转换一次。

### 修复

**尺寸永远从设置里取，绝不从 `getSize()` 读回。**

```ts
const S = winSize()          // 唯一真源：settings.windowSize
mainWindow.setBounds({ x, y, width: S, height: S })
```

写常量就不可能累积。配套：

- `WindowManager` 构造函数注入 `canonicalSize: () => number`，吸附时也用它而不是 `cur.width`，顺带把别处漏进来的漂移一并纠正
- `win:drag-end` 增加一次校正 + `logSize('drag-end-correct')`，异常尺寸可追溯
- 渲染层 `resize` 监听加**边长实际变化**判据，忽略同尺寸事件（避免拖动时反复重建 canvas）

## 三、窗体偶发自己移动

### 根因

`move` 事件的 150ms 防抖定时器**回调里没有重新检查 `dragging`**：

```ts
moveTimer = setTimeout(() => {
  winMgr?.dockToTaskbar()      // 旧代码：无条件执行
}, 150)
```

定时器被安排后，如果用户在这 150ms 内开始拖动，定时器照样触发 `dockToTaskbar()`，把窗口拽到任务栏 —— 表现为「窗体自己动了」。

另一个诱因是尺寸切换里的 `setResizable(true/false)` 来回切：它会重写 Win32 窗口样式，本身就可能让窗口位移。

### 修复

- 定时器回调里重新校验 `dragging` / `dragEndTs` / `autoDock`
- 尺寸切换不再动 `resizable`，只放开 min/max 约束

## 四、其他配套改动

| 改动 | 原因 |
|---|---|
| `clearRect(0,0,size,size)` → `clearRect(0,0,sz,sz)` | `size` 是窗口设置值，和画布单位会脱节，导致清不干净留拖影 |
| 依赖数组 `[shape]` → `[shape, size, viewTick]` | 原来改尺寸后 `COLS/CELL/K1/canvas.width` 全是旧值，只靠 CSS 拉伸 |
| A/B/colorShift 提升为 ref | resize/换形状重建画布时，旋转姿态不再被打回初始值 |
| 字形改 `textAlign:'center' + textBaseline:'middle'` | 消除左上角锚点导致的近一格系统性偏移 |
| `border: 1.5px` → `box-shadow: inset` | 边框会吃掉布局空间，每边少 1.5px 填充 |
| 命中测试改用 canvas 实际 rect 换算 | 不再假设 CSS 尺寸 == `size`，鼠标穿透判定更准 |
| `main.ts` 尺寸切换补 `setBounds` | 原来只调 min/max + `setPosition`，窗口是否真的变大全靠平台隐式行为；且居中补偿用的是旧宽度 |

> **通用教训**：任何「读回当前状态 → 加工 → 写回去」的高频循环，只要读写之间存在有损转换（取整、单位换算、钳制），就会单调漂移。窗口尺寸、滚动位置、缩放比例都踩过这个坑。写入必须来自**独立的真源**，而不是上一次的测量结果。

## 五、字符密度

放大形状之后暴露出三个独立的密度问题。

### 5.1 球体光照方向反了（主因）

```ts
const L = -(xr * 0.45 + yr * 0.55 - zr * 0.7)   // 旧代码
```

展开是 `-0.45xr - 0.55yr + 0.7zr`，即光源方向 `(-0.45, -0.55, +0.7)` —— **指向屏幕里面**。而可见半球是 `zr < 0`（朝向观察者），所以球心处 `L = -0.7 < 0`，是暗的。

实测：**只有可见圆面的 2.7% 被点亮**，渲染出来是边缘一道细牙。这才是「球体看不清楚」的真正原因，采样稀疏只是次要。

修正为光源朝向观察者：

```ts
const L = -(xr * 0.45 - yr * 0.55 + zr * 0.7)   // = -0.45xr + 0.55yr - 0.7zr
```

点亮比例 **2.7% → 97.3%**，球心 `L = +0.70`。顺带 `FIT.sphere` 也重新标定了：原来的 `k=1.123, ox=0.583, oy=0.394` 是在拟合那道 2.7% 的细牙，所以偏心得离谱；修正后 lit 集合居中，回到 `k=0.963, ox=0.5, oy=0.5`。

### 5.2 采样步长写死，格子数却随窗口增长

角步长 `dth=0.07 / dph=0.04` 是常数，但 COLS 随窗口线性增长。放大形状后覆盖率：

| 窗口 | 甜甜圈 | 球体 |
|---|---|---|
| 220 | 99% | 53% |
| 320 | 99% | 29% |
| 480 | 93% | 14% |
| 640 | **76%** | **8%** |

**甜甜圈**：改为从投影尺度反推步长 —— `cellsPerUnit = K1x / (K2 - (R1+R2))`（最近点处一个 3D 单位长度跨多少格），步长取 `SAMPLE_GAP / cellsPerUnit`。`SAMPLE_GAP = 1.4` 实测各尺寸覆盖率 ≥98.8%，减半只换来 +0.3%。另加 `MAX_SAMPLES = 90k` 上限：640px 下诚实执行要 192k 采样/帧（~400M flops/s，JS 扛不住），降到 90k 只损失 0.2% 覆盖率。

角度在画布生命周期内固定，因此 cos/sin 预计算成查表，热循环里零三角函数。

**球体**：改为**屏幕空间反投影** —— 遍历格子而不是遍历表面。球的轮廓在任何姿态下都是圆，反解投影即可：

```
u = xr/(2.2+zr), v = yr/(2.2+zr) 在单位球上
=> (m+1)t² - 4.4t + 3.84 = 0,  m = u²+v²,  t = 2.2+zr
```

取较小根即近表面。判别式 `D = 4 - 15.36m ≥ 0` 给出轮廓半径 `sqrt(4/15.36) = 0.5103` —— 与独立测出的包围盒完全一致，交叉验证通过。每个格子命中恰好一次，**覆盖率 100% 且代价是 O(格子数)**；靠加密表面采样达到同样效果需要约 300k 采样/帧。

颜色带需要物体空间经度，用逆旋转还原（先绕 X 转 -A，再绕 Y 转 -B）。

### 5.3 字号是格子的 2 倍，字形互相盖住

```ts
ctx.font = `${Math.max(9, Math.round(CELL + 2))}px ...`   // 旧代码
```

`COLS = sz/4.5` 意味着 `CELL` 恒为 4.5px，于是 `max(9, 7)` 恒为 **9px** —— 字形是格子的 2 倍，上下行严重重叠，明暗渐变 `.,-~:;=!*#$@` 被糊成色块。

**修法不是简单把字号调小**：等宽字形的步进宽度只有字号的 ~0.55em，而竖直占满 1em。正方形格子只能匹配一个轴 —— 字号贴合行高则每格水平空 40%（形状变点阵），贴合宽度则行间重叠。

正解是**让格子跟随字形长宽比**（donut.c 里 x 乘 2 就是干这个的，这里改成运行时 `measureText` 实测而非猜）：

```ts
ctx.font = `${FONT_PX}px Consolas, ...`
const CELL_W = ctx.measureText('M').width   // 实测步进
const CELL_H = FONT_PX * LINE_RATIO
const COLS = round(sz / CELL_W)             // 横向格子更多
const ROWS = round(sz / CELL_H)
```

投影侧对应拆成 `K1x = fit.k * COLS` 和 `K1y = fit.k * ROWS`。两轴的**像素**尺度相同，所以形状不变形。

`FONT_PX = 5.6`、`LINE_RATIO = 0.85`，220px 窗口下格子 3.08×4.76px、网格 71×46，字形恰好平铺不重叠。

| 窗口 | 网格 | 甜甜圈字符数 | 球体字符数 |
|---|---|---|---|
| 180 | 58×38 | 811 | 1625 |
| 220 | 71×46 | 1180 | 2418 |
| 320 | 104×67 | 2450 | 5148 |
| 640 | 208×134 | 9496 | 20585 |

## 六、字符可见性（"不够明显"）

用户反馈形状"不够明显"，问是配色还是字符问题。量下来**两者都有，且字符阶梯的问题更大**。

### 6.1 字符阶梯没归一化（bug）

甜甜圈的 `L` 真实范围是 `-1.902 ~ 1.901`（数值扫描所有姿态得出），但代码写的是：

```ts
CHARS[Math.min(CHARS.length - 1, (L * 8) | 0)]    // 旧代码
```

要 `L ≥ 1.125` 才用得上 `#`，`L ≥ 1.375` 才到 `@`。很多姿态下 `L` 根本到不了：

| 姿态 | 暗端字符占比 | 平均墨水覆盖 | `#$@` 使用率 |
|---|---|---|---|
| A=0.9, B=0.4 | 29% | 33.9% | 正常 |
| A=1.6, B=2.2 | 64% | 14.3% | **0%** |
| 球体 | 80% | 13.6% | 13% |

后果是**亮字符随姿态时有时无**，转着转着整体就淡下去了。修法是按 `DONUT_LMAX = 1.902` 归一化后再套 gamma。

### 6.2 配色是个无解的结构问题

这是透明窗口，浮在任意桌面上。实测各档亮度对三种背景的对比度：

| 配色 | 深色任务栏 | 浅色桌面 | 中灰壁纸 |
|---|---|---|---|
| L=0.30（原） | 1.3~5.0 | 2.8~11.0 | 1.0~3.2 |
| L=0.50 | 2.3~11.0 | 1.3~6.3 | 1.0~2.7 |
| L=0.70 | 5.1~13.8 | 1.0~2.8 | 1.2~3.3 |

**没有任何一档能通吃** —— 最低对比度永远掉到 1.0 附近。单纯调配色是拆东墙补西墙。

结构性解法是**描边**：描边打底 + 亮色填充，对比度就锚定在描边上，与桌面无关（描边是深色但不必是纯黑）。

关键连带结论：**描边打开后，最优字色亮度也变了**。字色此时是跟黑色描边比对比度，而不是跟桌面：

| 字色亮度 | vs 黑色描边的平均对比度 |
|---|---|
| L=0.30（原） | 3.6 |
| L=0.58 | **9.0** |

所以配色跟随描边开关走：描边开 → `L=0.58`（亮，锚在描边上）；描边关 → 保持 `L=0.30` 原始暗色调（没有锚点，不如别假装）。

### 6.3 做成设置项

三个杠杆合并成两个托盘菜单项，默认开启但可关：

- **🔡 字符浓度**：清淡 / 标准 / 浓密 —— 映射到 (gamma, 字符集) 预设
- **🖊 字符描边**：开 / 关 —— 同时切换配色亮度

`density` 预设：

| 档位 | gamma | 字符集 |
|---|---|---|
| light | 1.0 | `.,-~:;=!*#$@` |
| normal | 0.6 | `.,-~:;=!*#$@` |
| dense | 0.5 | `-~:=+*#%$@`（去掉 2~3% 墨水的 `.` `,`，补中间调 `+` `%`） |

实测平均墨水覆盖率：

| 浓度 | 甜甜圈 A=0.9 | 甜甜圈 A=1.6 | 球体 |
|---|---|---|---|
| light | 20.3% | 10.3% | 13.6% |
| **normal（默认）** | **29.4%** | **15.8%** | **20.1%** |
| dense | 39.2% | 35.6% | 34.2% |
| *修复前* | *33.9%* | *14.3%* | *13.6%* |

三档都用满了字符阶梯（无未使用字符）。注意 `dense` 的跨姿态一致性明显更好（39.2% vs 35.6%），而 `light` 波动大（20.3% vs 10.3%）—— gamma 越小压缩越少。

描边渲染是两趟：先一次性描完所有字（`strokeStyle` 只设一次），再填充。不能逐字 stroke-then-fill，否则邻居的描边会啃掉已经填好的字。填充趟加了 `fillStyle` 变更判据 —— 甜甜圈按环序产出、每环同色，几千次状态切换塌缩成约 16 次，基本抵掉描边趟的开销。

## 七、球体不旋转

### 根因：球的一切都是姿态无关的

改用屏幕空间反投影后，球体看起来完全不转了。原因不是回归，而是**它本来就没转过** —— 以前被 2.7% 那道锯齿牙的采样抖动掩盖了。

球的轮廓在任何姿态下都是同一个圆，而 `L` 只由视空间的 `(xr, yr, zr)` 决定，同一个格子在任何 `A/B` 下算出的 `L` 完全相同。**光照和轮廓双双姿态无关**，所以字符图案是死的，只有颜色在流动。

### 修复

让字符阶梯额外骑在**物体空间**纹理上（用逆旋转还原的经度 `lon` 和纬度正弦 `y0`）：

```ts
const tex = 0.5 + 0.5 * Math.cos(lon * 6) * Math.cos(y0 * 6)
const shade = L * (0.6 + 0.4 * tex)
```

甜甜圈不需要这个 —— 它的轮廓本身就随旋转变化。

## 八、窗体难以选中

### 根因

像素级穿透判定取的是光标**正下方那一个像素**的 alpha：

```ts
const px = ctx.getImageData(lx * dpr, ly * dpr, 1, 1).data[3]
applyIgnore(px < 16)
```

但 ASCII art 的平均墨水覆盖率只有 ~14%（见 6.1）—— 光标下 86% 的概率落在字符之间的空隙里，判定为"穿透"。所以感觉必须精准戳到某个字符才能选中窗口。

### 修复

改成**邻域判定**：光标周围 `HIT_RADIUS = 7` CSS px 的方形区域内有任何墨水就算命中。空白角落依然可以穿透点到桌面，穿透特性没丢。

## 九、球体改地球仪

把"球体"形状替换成地球仪。海陆来自一张 5° 分辨率的陆地掩码（`LAND`，72×36 位图，'1' = 陆），按物体空间经纬度查表：

```ts
const lat = Math.asin(y0)
const lon = Math.atan2(z0, x0)
const glat = (87.5 - lat·57.29578) / 5   // -> mask row
const glon = (lon·57.29578 + 180) / 5    // -> mask col
```

大陆是**物体空间**的特征，所以球转起来大陆跟着转 —— 比之前那个纯色球自然得多，也顺带彻底解决了"球体不转"的问题（七节那个抽象纹理在这里直接换成了真大陆）。

掩码不是拿真实海岸线数据压缩的，而是按大陆的经纬度包围盒手工描边、再转成 ASCII 目视校对，最后按 `cos(lat)` 面积加权验证陆地占比（34.3%，真实值约 29% —— 5° 分辨率下这个量级是合理的）。其中"海"是第二遍抠出来的：地中海、黑海、红海、波斯湾、孟加拉湾、南海、加勒比、哈德逊湾、白令/鄂霍次克海。

配色用地球三色调（海洋蓝 / 陆地绿 / 极地白），每类预计算 8 档亮度阶梯，热循环里只做一次数组索引。关键调参：

- **海洋地板亮度 0.62**：否则暗侧的海洋会掉成黑色空间，球看起来像"大陆漂浮在虚空里"
- **海洋用更轻的字形**（shade × 0.7）：让海面平滑、陆地在视觉上更密
- **极地取消纬度衰减**：否则冰盖会被压暗成灰

菜单项从「🔵 球体」改成「🌍 地球仪」，内部仍复用 `sphere` 渲染分支。

## 十、长按不重复旋转

长按一个键时，OS 以系统重复率连续触发 `keydown`（auto-repeat），而 `uiohook-napi` 会把每个都原样抛出来 —— 导致长按期间甜甜圈不停地转、按键统计也被虚增。

修法在 [hooks.ts](../electron/hooks.ts)：

```ts
private heldKeys = new Set<number>()
hook.on('keydown', (e) => {
  const code = e.keycode
  if (this.heldKeys.has(code)) return   // OS auto-repeat — drop
  this.heldKeys.add(code)
  ...
})
hook.on('keyup', (e) => this.heldKeys.delete(e.keycode))
```

按下第一次计数，直到 `keyup` 才允许下次。`stop()` 时清空。回退路径（渲染进程 `keydown`）同步加 `if (!e.repeat)`。

> 这里的坑：不能把"长按"直接当一次也不想重复 —— 那会丢掉"按住不放每 N 秒跳一下"之类的合法重复意图。但本应用的输入是脉冲触发（敲一下转一下），按"按下算一次、松键前忽略"最贴切。

## 十一、验证结果

数值仿真，8100 个姿态全扫（COLS=71 即 320px 窗口）：

| | 填充率 min / avg / max | 裁切点数 | 旋转时尺寸变化 |
|---|---|---|---|
| 修复前 `K1f=0.345` | 44% / 47% / 49% | 0 | 无 |
| 逐帧自适应（已回退） | 91.5% / 93.9% / 97.2% | 0 | **±6%（实机可见抖动）** |
| **当前 `K1f=0.542`** | **64.8% / 74.4% / 93.0%** | **0** | **无** |

K1 系数 `0.345 → 0.542`，放大 **57%**。

## 十二、已知限制

- **填充率随姿态在 64.8%~93.0% 之间**。固定缩放必须按最坏姿态（环面正对观察者、投影最大时）定尺寸，其余姿态就有余量。这是固定缩放的固有代价，换来的是尺寸绝对静止。
- **留白最多有 21 格不对称**。包围盒非正方形时按长边等比缩放，短边方向必然留余量；强行两个方向都填满需要非等比拉伸，会导致形状变形。

## 十三、主题 / 配色 / 随机转向 / 地球仪精度

> 注：本节与[十四](#十四外观系统五个独立维度)记录的是演进过程；其中「跟随系统」「描边」「边缘(edge)」等方案后来被简化。**最终外观模型见[十五](#十五外观模型最终)**。

一次迭代把外观相关的四个诉求一起落地。

### 13.1 主题替换描边

描边方案被放弃，改成**深浅主题**。新增 `theme: 'auto' | 'dark' | 'light'`（默认 `auto`）：

- `auto` → 跟随系统主题 `nativeTheme.shouldUseDarkColors`（跟随的是系统深浅色，不是壁纸实际明暗）
- `dark` → 深色背景，配色走亮色
- `light` → 浅色背景，配色走暗色

主进程新增 `app:dark` IPC，把 `theme` 解析成布尔 `dark` 返回；`nativeTheme.on('updated')` 触发 `pushSettings` 让 `auto` 在系统主题变化时自动刷新，无需重启。

### 13.2 多配色主题 + 自定义

新增 `palette`（默认 `rainbow`），托盘「🎨 配色」子菜单：

| id | 名称 | 说明 |
|---|---|---|
| rainbow | 彩虹 | 0→360° 色相旋转 |
| neon | 霓虹 | 青→品红 |
| sunset | 日落 | 橙→粉→紫 |
| ocean | 海洋 | 蓝→青 |
| mono | 单色 | 金色明暗阶梯 |
| custom | 自定义 | 读 `userData/keepboard-palette.json` |

自定义文件格式：

```json
{
  "chars": ".,-~:;=!*#$@",
  "gamma": 0.6,
  "colors": ["#ff3355", "#ff9933", "#ffee33", "#55ee55", "#33ccff", "#8855ff"]
}
```

`chars` 是明暗阶梯、`gamma` 是阶梯权重、`colors` 是任意数量的 hex，渲染时插值成 16 步渐变。`colors` 缺省回退到 rainbow；`chars`/`gamma` 缺省沿用当前字符浓度档。

配色内部全部改成「HSL→RGB 元组 + 亮度因子」：预设生成 16 步渐变，再统一乘 `dark ? 1 : 0.55` 的亮度因子，所以同一套预设深浅主题下自动适配。

### 13.3 随机转向

新增 `randomSpin`（默认 `false`，保持原行为）。开启后每次输入触发冲量时随机掷一个方向：

方向有惯性：只在**停下后重新启动**时才重新随机，转动期间保持。逐次按键各自掷方向会导致快速敲键时"左一下右一下"：

```ts
if (randomSpin && velB.current === 0 && velA.current === 0) {
  spinDirRef.current = Math.random() < 0.5 ? -1 : 1
}
const dir = randomSpin ? spinDirRef.current : 1
velB.current = clamp(velB.current + dir * 1.0 * s, -MAX_VEL_B, MAX_VEL_B)
velA.current = clamp(velA.current + dir * 0.45 * s, -MAX_VEL_A, MAX_VEL_A)
```

衰减从单边 `vel < 0.02` 改成 `Math.abs(vel) < 0.02`，速度钳制从 `Math.min` 改成 `±MAX`，支持负向。

### 13.4 地球仪 2° 掩码 + 自适应密度

海陆掩码从 5°（72×36）提到 **2°（180×90）**，补了日本、马达加斯加、印尼、菲律宾、新西兰等岛屿；内陆海（地中海/黑海/红海/波斯湾/孟加拉湾/南海/加勒比/哈德逊湾/白令）仍做二次抠除。面积加权陆地占比 33.1%。

字符字号从固定 5.6px 改成**随窗口缩放**：

```ts
const FONT_PX = Math.max(4.2, Math.min(6.4, 6.6 - (sz - 220) / 420 * 2.4))
```

220px 窗口 6.6px、640px 窗口 4.2px —— 大窗口渲染更细的字符，大陆边缘不再有阶梯感。

## 十四、外观系统：五个独立维度

「深浅主题」这个维度太小了，把外观重构为**五个正交维度 + 命名预设 + JSON 自定义**。

### 五个维度

| 维度 | 取值 | 说明 |
|---|---|---|
| `charset` 字符集 | ascii / block / dot / line | 明暗阶梯的字形风格，观感变化最大 |
| `tone` 明度 | night / dark / mid / bright / high | 整体亮度，**与背景解耦**，纯审美 |
| `saturation` 饱和度 | gray / muted / normal / vivid / neon | 鲜艳度 |
| `palette` 色相 | rainbow/neon/sunset/ocean/mono/aurora/cyber/candy/gold/forest | 色相渐变（多停点插值） |
| `edge` 边缘 | none / outline / glow / bloom | 描边 / 光晕，负责任意桌面下的可读性 |

关键变化：**明度(`tone`)从「背景适配」里拆出来了**。原来的 `theme`(dark/light) 只改一个亮度因子，现在 `tone` 是纯审美明度，而 `theme`(背景) 只负责光晕/描边的极性（深背景→亮光晕，浅背景→暗光晕）。所以「深色调 + 浅色背景」这种组合天然成立——色调是调出来的，可读性交给 edge。

### 命名预设

托盘「🎨 外观」子菜单列 11 个 look + 自定义，每个是一组五维组合：

classic / neon / cyber / aurora / sunset / ocean / forest / candy / pixel / dot / gold / custom

完整定义在 `PetCanvas.tsx` 的 `LOOKS`。

### 自定义 look

`userData/keepboard-look.json` 支持**多套**自定义外观，每套带 `id` / `name` / `icon`：

```json
{
  "looks": [
    {
      "id": "custom-neon",
      "name": "我的霓虹",
      "icon": "🎇",
      "tone": "bright",
      "saturation": "neon",
      "palette": "cyber",
      "gamma": 0.6,
      "colors": ["#ff00aa", "#00ffff"]
    }
  ]
}
```

这些外观出现在「配色」子菜单的内置预设下方（用一条横线隔开），底部还有「📂 打开配置文件」——点击会创建默认文件（如果还没有）并打开它。`colors` 覆盖 `palette`（插值成 16 步）；`chars` 可直接覆盖整个明暗阶梯；其余字段缺省回退 `classic`。

### 渲染

配色改为「HSL→RGB 元组 + 亮度因子」：预设生成 16 步渐变再统一乘 `tone`。地球仪仍用地球三色调，但整体亮度也由 `tone` 缩放（不再由背景决定）。「✨ 光晕」是独立开关，打开时在填充下打一层极性跟随 `dark`（背景）的软光晕，半径和透明度都刻意调小，避免字符糊成一片。

## 十五、外观模型（最终）

经过几轮反馈后的最终外观设置，分五个独立的开关/预设，各自独立、互不覆盖：

| 设置 | 取值 | 说明 |
|---|---|---|
| `look` | classic / neon / cyber / aurora / sunset / ocean / forest / candy / gold / 自定义 id | 只含**色相 + 明度 + 饱和度**（+ gamma/colors/chars） |
| `charset` | ascii / block / dot / line | 字符集风格，独立开关 |
| `glow` | 布尔 | 光晕开关（默认关），极性跟随背景 |
| `theme` | dark / light | 背景（只决定光晕极性），无「跟随系统」 |
| `randomSpin` | 布尔 | 随机转向开关（带惯性：停下才重掷方向） |

### 配色子菜单结构

```
（内置 9 个预设）
─────────────────
🎇 我的霓虹      ← 自定义外观（id + name + icon）
🌙 暗夜极光
─────────────────
📂 打开配置文件
```

### 自定义外观文件

`userData/keepboard-look.json`，多套列表，每套带 `id`/`name`/`icon` 和 LookDef 字段（`tone`/`saturation`/`palette`/`gamma`/`colors`/`chars`）。文件不存在时点「打开配置文件」自动创建一份带 `custom-neon` 示例的文件。菜单每次右键实时重读，选中即存 `id`。

### 光晕

「✨ 光晕」是独立开关（默认关）。打开时在填充下打一层极性跟随 `dark`（背景）的软光晕（`shadowBlur ≈ 0.4×字号`、低 alpha），避免像早期版本那样每个字符叠一层阴影糊成一片。
